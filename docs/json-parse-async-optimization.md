# JSON.parseAsync 优化计划与验收记录

基线提交：`a7a56c174`。本轮目标是改善真实并行吞吐，同时保持 JSON 语义、主线程让步和销毁安全；不以增加线程数掩盖额外 CPU / 内存成本。

## 目标与执行顺序

| 目标 | 实施内容 | 验收方式 |
| --- | --- | --- |
| G1 建立可比基线 | 保存原二进制；增加关闭 DCHECK 的 release 对照；固定 worker 数、交替执行同步/异步，包含不同内容的文档 | 相同输入、编译配置、线程数和保留结果方式；输出逐轮数据、中位数、CPU 与峰值内存 |
| G2 降低前台成本 | 基于测量优化同类数组批量填充、临时句柄、数值表示与对象构建；保留 GC / Map 安全检查 | 对象密集路径相对原异步版本有可重复收益；同步基线不因重构退化 |
| G3 降低原生数据成本 | 评估记录存储、扩容和生命周期，避免输入、记录、结果长期叠加 | 记录字节数可直接核算；大输入峰值内存与总耗时对照，不采用盲目按字节预留 |
| G4 复用与优化词法 | 抽取真正无堆依赖的扫描原语，同步/异步共享；评估后台预解码转义字符串 | 语法错误、Unicode、数字边界差分通过；无转义和带转义场景分别测量 |
| G5 选择合理流水化边界 | 评估是否需要同文档生产/消费流水线；保留优于复杂流水线的简单方案 | 必须核对容器计数、错误末尾、取消、发布顺序、GC 根和内存占用；无证据不引入通用队列/额外 isolate |
| G6 回归与交付 | 重跑语义、并发、GC、终止/销毁、依赖检查和基准，记录保留/撤回的实验 | 正确性检查全部通过，性能数据与限制可复现，不声称任意输入必然加速 |

性能验收关注端到端完成时间、主线程最大片段、CPU 与峰值内存。主要工作负载出现超过约 5% 的可重复回退时先复核噪声，再修正或撤回方案；单项极端快路径不应牺牲普通对象场景。百分比阈值是实验筛选规则，不是可移植性能保证。

## 已知证据与约束

- 原测量约 2.4 MB 对象数组：同步 42.649 ms；异步调用 0.887 ms、等待 9.360 ms、前台任务 41.441 ms，总计 51.689 ms。等待不是后台 CPU 时间；前台包含 GC 和清理。
- 原生记录每条 16 字节，该对象输入约 500002 条，即约 8 MB 有效记录，尚未计入 vector 预留容量、输入副本和 JS 对象。
- 对象构建、Map 操作和 reviver 必须遵守调用方 isolate 的线程约束。工作线程不能直接解引用其普通 JS 堆对象；禁止通过关闭 GC / 写屏障换取表面提速。
- 已有 Map feedback、原 BuildJsonObject / BuildJsonArray 和大数组直接填充，不重复实现这些已有优化。
- 工作线程扫描所有数据后才发布前台任务；容器结束位置和元素数量完成后才可用。流水化不是简单提前 PostTask，不能并发读写正在扩容的 vector。
- 保持输入 ToString、重复键、索引键、孤立代理项、负零、reviver context.source、realm、异常和执行终止语义。

## 验证入口

现有语义与性能入口分别为 `test/json/parse-async.js`、`test/json/parse-async-benchmark.js`；原生回归为 `test/cctest/test-json-async.cc`。本地构建产物和实验日志放在已忽略的 `out/`，不提交二进制。

固定 8 个 worker、同时提交 16 份 JSON、9 轮中位数；此模式不夹带同步解析。CPU 为整个基准子进程的 user + system 时间，RSS 为整个进程的峰值；两者仍包含输入准备、显式 GC 和运行时启动，不是仅解析函数的计数。

| --- | ---: | ---: | ---: | ---: |
| 普通对象 | 142.225 → 114.896 | -19.2% | 3.956 → 3.590 | 717.5 → 476.1 |
| 数值数组 | 13.981 → 9.080 | -35.1% | 0.536 → 0.442 | 166.8 → 124.2 |

## 架构取舍与实验记录

- **保留分块回收，未引入跨线程流水化。**后台仍先完成校验和容器计数，再一次发布不可变结果；前台每片结束时回收已消费块。不同文档本来可以重叠执行。这个方案在已测多任务场景减少峰值内存和开销，不需要未知长度数组反复增长、跨线程可变容器或早期结果暴露。单文档扫描与构建仍不重叠，这是明确保留的限制。
- **预解码撤回。**试验将长转义字符串解码到原生 UTF-16 缓冲区，前台再复制。对照 9 轮，长字符串四任务从 6.042 ms 变为 7.943 ms，峰值 RSS 从约 97.5 MiB 变为 161.4 MiB；额外缓冲/复制不合算。原型源码已撤回，没有保留死代码或未使用开关。
- **记录存储实测选择 deque。**紧凑 vector 版本与分块版本第一次对照的单任务普通对象出现约 5.8% 波动，随后反向顺序复测 20 轮，差距约 1.9%、CPU 基本持平，峰值 RSS 更低；多任务和不同内容对象更有收益，故保留标准容器而非新增自定义 arena。
- **缓存有边界。**64 个槽只在单次解析中有效；冲突比较实际字符，冲突不覆盖已有槽。它不共享可变 HeapNumber，不跨 isolate，不改变 reviver 的源码映射。
- **安全边界不放宽。**对象分配、Map 检查、GC 根、写屏障和 reviver 仍在正确线程；单个大字符串、大对象、输入复制、GC 和 reviver 仍可能超过软预算。external memory 是估计，不包含 deque 块余量/分配器管理开销，也不提供任务内存配额。

## 可复现命令与证据

在仓库根目录，保留的本机二进制与脚本可直接运行：

```sh
python3 test/json/parse-async-benchmark.py out/json-opt-baseline/d8-release out/json-opt-release/d8 --runs 11 --workers 4
python3 test/json/parse-async-benchmark.py out/json-opt-baseline/d8-release out/json-opt-release/d8 --mode async --runs 9 --workers 8 --jobs 16 --cases records numbers varied
python3 test/json/parse-async-benchmark.py out/json-opt-baseline/d8-release out/json-opt-release/d8 --mode sync --runs 15 --workers 4 --jobs 4
out/json-async/d8 --expose-gc --stress-compaction test/json/parse-async.js
out/json-async/cctest-json-async test-json-async/JsonParseAsyncCompactRecords
```

换机器时须从基线提交和优化源码分别使用相同 GN 参数构建，不能把另一配置的二进制当作对照。构建配置、二进制摘要和基线提交记在 `out/json-opt-final-provenance.json`。基准输入长度字段为 UTF-16 code units，不把 Unicode 输入的字符数误称为字节数。脚本输出逐轮样本，支持 both / sync / async 模式；CPU/RSS 在不支持 wait4 的平台标为不可用。

| 证据 | 发现 | 对应实现/决策 |
| --- | --- | --- |
| `out/json-opt-profile.txt` | 对象构建和字符串内部化是活跃调用栈；采样与编译并行，仅用于定位而非计时 | 保留原对象构建器，增加有界短字符串复用和批量原语填充 |
| `out/json-opt-final-benchmark.jsonl`、`out/json-opt-final-concurrency.jsonl` | 单/多任务端到端收益与同步差距 | 保留实测有效路径，明确普通对象低并发限制 |
