# 同形 JSON 对象直接构建：Mac ARM64 实验与撤回记录

> 后续诊断与修复已完成，见 [JSON.parseAsync 并发回退修复](json-parse-async-stack.md)。本文保留首轮撤回时的状态和全部负面结果；最终保留决定以该后续报告为准。

日期：2026-10-25。**最终没有保留生产优化。** 同步目标场景存在可重复收益，
但候选没有同时满足异步控制组的回退门槛。C++ 生产源码及本机 Release 构建已

## 基线与实验约束

- 冻结基线：`5ff8b43bf071712acb1c71efeb392a132ef6c0a9`，已包含 Mac 数值数组、字符串扫描和最新后台数字融合。
- Apple M1 Pro / macOS 27.0.1 / ARM64，Release `-O3`，无 LTO/PGO，沿用 `out/host/args.gn`。
- 生产源码修改前保存 `initial`；构建图重建后的 `baseline` 与其源码、参数及 d8/cctest 二进制完全一致。
- 上游参考固定为 [V8 831f844b 的 JSON parser](https://chromium.googlesource.com/v8/v8/+/831f844b72acbdf96d62e5aca8629ce0af5a707f/src/json/json-parser.cc)。没有升级整个引擎。
- 不改变 API、数字转换算法、原生记录格式、输入所有权、线程池或 2 ms 前台软预算。
- 按场景判断收益，汇总耗时或逐轮配对变化中位数出现约 5% 以上回退时复核；不以目标场景收益抵消控制组回退。
- 编译与正式计时不重叠。未锁核，进程负载和执行顺序保存在原始记录中。

## 测量方法

最终评估的有效候选为 `builder-entry-rebuilt`，不是早期同名但混合了头文件版本的构建。
主矩阵包含 31 类输入、1/4 个任务、固定 4 个 worker、四轮相邻独立进程配对；
每轮交换基线/候选顺序，每进程预热两次、每种 API 测量 15 次。共 **496 个进程、
14,880 个计时批次、124 个 sync/async 比较项**。四任务值为整批完成时间。

同步和异步在主矩阵中分别计时、交替执行。另有四轮独立 sync 对照，以及独立 async
复测。输入生成、显式计时前 GC 和输出校验不计入 API 延迟；计时内自然 GC 保留。
异步计时包含入口复制、调度、后台解析、前台构建与 Promise 完成。31 类输入及预期
输出的 UTF-16LE 长度和内容 SHA-256 均与冻结基线一致。

耗时降低比例为 `1 - 候选/基线`；负值表示变慢。绝对值为各进程中位数的中位数。
下表描述的是**已撤回候选**，当前恢复的生产版本不包含这些加速。

## 实现路线与撤回记录

有效候选沿用上游的思路：完整匹配属性序列后复用反馈 Map，检查对象布局、字段表示
和 FieldType，再使用现有折叠 HeapNumber 分配与写屏障直接构建。Smi 写入 double
字段时仍分配独立可变数值存储；reviver 保持原构建路径。

最终评估版本把快路径放在 `BuildJsonObject` 入口，保留原 `ParseJsonObject` 的
构建/返回调用结构。异步直接构建适配没有进入该版本。

| 候选 | 观察 | 决定 |
|---|---|---|
| sync：输出参数传递匹配标记 | 同步目标有收益，但 shape_churn 四任务同步增加 8.2%；独立 async 对象复测仍明显回退 | 撤回 |
| sync-cont / accepted：continuation 标记、词法解析器调用 helper | 扩大到 31 类输入后，前缀形状同步单/四任务增加 8.7%/9.8% | 撤回；完整矩阵保留 |
| combined：异步缓存键直接构建 | 未填充键缓存槽的空字符串哨兵误匹配上一对象的空键；原 parse-async 套件发现 | 正确性失败，未计时 |
| combined-fixed | 修复后 33 项检查通过；相对 sync-cont，四任务 async 普通/12 字段/嵌套对象增加约 7.2%/9.1%/9.2% | 异步适配撤回 |
| count-guard | 提前检查字段数仍不能消除前缀形状同步约 8% 回退 | 撤回 |
| result-status | 通过返回状态携带匹配结果，仍有前缀形状及异步并发回退 | 撤回 |
| object-handle、builder-entry 的最初构建 | 恢复源文件保留旧时间戳，导致部分依赖未重编译 | 无效构建，排除所有结论 |
| builder-entry-rebuilt | 完整重建后正确性通过，同步前缀回退消失；最终 31 类主矩阵仍有异步控制组回退 | 撤回 |
| builder-aligned：ARM64 入口 64 字节对齐 | 四轮对照出现更多同步及异步回退 | 撤回，对齐注解未保留 |

异步缓存错误的最小复现为 `[{"id":0,"":1},{"id":1,"Aa":2}]`：失败候选把
第二个对象的 `Aa` 键构建为 `""`。修复版排除了未填充槽，并加入了定向回归；
修复后仍因性能门槛未通过而撤回。

采样发现首个变体的热点包含后台解析循环。反汇编比较及多种接入位置的结果提示
生成代码布局/内联选择的敏感性，但没有确认完整的微架构根因。固定入口对齐实验
也失败了，因此不能把所有回退都简单归因于某一个对齐值。

## 构建前提修正

`object-handle` 和最初的 `builder-entry` 从快照恢复头文件时使用了保留时间戳的
复制，Ninja 因而复用了部分旧定义的目标文件。这两份构建的结果单独标为无效。
同一份 builder-entry 源码在强制重建全部头文件依赖后产生了不同二进制，之前的
同步/异步不一致也消失。后续恢复采用内容复制并刷新时间戳，不再保留源文件旧时间。

最终候选的再次完整恢复/重建与正确冻结二进制逐字节一致；最初基线以及更早的
有效候选不受该问题影响。证据见 `build-premise-correction.json`、
`builder-rebuild-identity.json` 和 `final-builder-restore-identity.json`。无效原始
文件依然保留，未混入最终 496 进程矩阵。
