## 根因与因果对照

后台 `BackgroundJsonParser` 使用 `std::vector<Frame>` 保存容器层级。
`Frame` 为 8 字节，常见对象数组的深度为 2，因此只申请 16 字节的堆缓冲区。
每个属性都会更新对象帧的 `key_count` 和 `cached_keys`。不同 worker 的缓冲区可能
落进同一个 128 字节缓存行，独立字段的频繁写入导致缓存行在核心之间来回转移。
这类伪共享使并发解析消耗更多 CPU 周期。

证据按定位顺序如下，全部原始数据保留：

1. 冻结基线与其逐字节副本的 A/A 对照也会变慢：60 字段对象四任务 async 汇总差异约
   10.2%，个别配对约 18%–19%，同步基本持平。因此不能把所有进程间差异都归因于候选代码。
2. 对确实变慢的旧候选分段计时，增加的主要是 worker CPU；前台构建、GC 和排队不能解释差额。
   按性能核心/效率核心记录的指令与周期表明，慢样本主要仍在性能核心执行，指令数接近而周期数增加。
   诊断使用了 [Apple XNU 的线程计数器定义](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/resource_private.h)，以及本机 SDK 的线程 CPU 编号接口。
3. 记录容器栈地址，按本机实际 `hw.cachelinesize=128` 分组。12 字段对象没有共享缓存行时，
   每批最慢 worker 的 CPU 中位数约 11.6 ms；出现共享时约 17.9–19.9 ms。
4. 用**同一个 cctest 二进制**进行因果对照：环境开关只决定是否在解析前
   `stack_.reserve(16)`，解析循环保持相同。相邻独立进程按轮次交换执行顺序，
   每侧、每种输入均有 4 轮 × 9 个计时批次。默认缓冲区每侧 36/36 轮发生共享，
   预留存储每侧 0/36 轮发生共享。

| 输入，四个 worker | 默认小堆块：最慢 worker CPU 中位数 | 预留独立存储 | 默认/预留的 p90 |
|---|---:|---:|---:|
| records12 | 24.511 ms | 11.938 ms | 25.820 / 13.149 ms |
| records60 | 44.099 ms | 18.376 ms | 49.929 / 19.205 ms |

这些是诊断程序中的后台 CPU 时间，不能与 d8 的 API 总延迟混用。
对照中的前台构建与 GC 时间相近。后续使用正式 `SmallVector` 修复的计数器诊断，
12/60 字段各 54 批的最慢 worker CPU 中位数约为 11.53/18.29 ms。

最初采样热点包含数字扫描，函数布局和内联曾被怀疑；地址记录与同二进制对照把根因
进一步定位到了容器栈伪共享。单看热点地址，不能证明数字算法或入口对齐有问题。

## 最终代码

- 后台容器栈改为 `base::SmallVector<Frame, 16>`。浅层帧位于各 worker 自己的栈中，
  消除这类小堆块伪共享；超过 16 层仍会动态扩容，16 不是解析深度限制。
- 同步解析沿用上一轮有效的 `builder-entry-rebuilt` 接入方式：完整匹配键序列后，
  检查反馈 Map、字段表示和 FieldType，直接分配并填写对象。使用现有折叠 HeapNumber
  分配，保留写屏障和不匹配时的原构建路径。
- async 前台继续使用原构建器；本轮异步收益来自后台容器栈修复。API、数值语义、
  线程优先级、任务调度和 2 ms 前台软预算保持原有规则。
- 正式代码的修改在三个文件中，共 80 行新增、1 行删除。计数器、环境开关、打印和临时
  cctest 平台修改只保留为诊断材料，没有留在生产/测试源码中。

## 最终组合对冻结基线的性能

主矩阵包含 31 类输入、单/四任务、4 个 worker，四轮相邻独立进程配对且交换执行顺序。
每进程预热两次、每 API 计时 15 次。同步/异步分别计时，在进程内交替执行。
输入生成、显式计时前 GC 和结果校验在计时区间外，计时内自然 GC 保留；async 包含入口复制、
