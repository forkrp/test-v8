# JSON.parseAsync 第三轮优化计划与验收记录

日期：2026-09-28。基线：`44b54c74051d578053b0d4a57157325e33f56e27`。

目标是减少主线程对象构建的重复工作，并改善大量并发 JSON 的有效吞吐，而非仅让 worker 更快。先保存基线，再进行有界原型、同配置对照与安全回归；没有可重复收益的方案撤回。完成后按用户授权本地 DCO 提交，远端推送必须另行二次确认。

## 目标与顺序

| 目标 | 实施 / 评估内容 | 验收条件 |
| --- | --- | --- |
| T1 基线与热点 | 保存 Release / DCHECK 二进制、参数与哈希，复核当前 Release 并发调用栈 | 不覆盖原二进制；明确采样不等同计时 |
| T2 有界键 / 结构复用 | 优先复用已验证属性键，减少前台 MakeString / 比较；保留原对象构建器、Map 与字段表示检查 | 缓存有界且解析内隔离；碰撞严格比较；重复键、索引键、Unicode、GC 和 reviver 正确 |
| T3 中间表示与并发内存 | 测量键复用的记录 / 根开销，评估紧凑记录或按在途字节限流 | 不用增加全局缓存或仅降低 worker 数冒充改进；CPU / RSS 与端到端同时检查 |
| T4 流水线及复制边界 | 判断同文档流水化、稳定所有权输入的少复制是否值得 | 无证据不引入跨线程可变对象；不借用可能被 GC 移动 / 释放的普通堆字符串裸指针 |
| T5 验证与交付 | 固定 4 / 8 worker 的单、多任务基准，反向复测、同步对照、GC / 销毁测试、文档和本地提交 | 有效改动保留，回退撤销；报告未解决限制；不推送 |

## 首个原型的边界

- 只复用不可变属性名称，不共享可变 HeapNumber 或 JSObject。
- 原型优先覆盖无 reviver 的有界小对象路径，避免给任意宽对象新增无界并行缓存。
- worker 只处理原生数据和缓存编号；V8 String 的内部化、根管理、Map 更新和对象分配仍在调用方 isolate。
- 继续调用原 `JSDataObjectBuilder`；不得因为缓存命中跳过字段表示、重复属性或失效 Map 的检查。
- 保持现有 12 字节记录及消费回收，保持 2 ms 软预算和取消检查；不增加独立 JSON 线程池。
- 如果额外后台哈希、句柄或适配分支抵消收益，撤回该原型，再选择更小的替代方案。

## 实验与验证规则

主要场景若出现超过约 5% 的可重复回退，先复核顺序 / 调度噪声，再修正或撤回。单任务和 4 任务使用固定 4 个平台 worker，16 任务使用固定 8 个平台 worker；这是共享线程池的配置容量，不保证每个 worker 始终在解析 JSON。不改线程数来掩盖开销。Release、DCHECK 分别报告，不混合不同比例或不同构建的数字。

除原有七类工作负载，针对缓存增加碰撞键、超过容量的键、交替对象结构、Unicode / 转义 / 数字键、重复键、宽对象和大缓存失效率检查。复用现有 JS 差分和定向 C++ 测试，不新增框架。

本机为 macOS x64、Release 关闭 DCHECK / i18n / sandbox，未验证生产 PGO、其他平台或完整 cctest 聚合套件。实验产物保存在忽略的 `out/json-opt3/`。必须分别披露初始同步复制、GC、单个大分配和 reviver 的长任务限制。

## 执行状态

目标已创建，计划先于代码落盘。基线 Release、DCHECK d8 和定向 cctest 已分别保存为 `out/json-opt3/baseline-*`，构建参数和 SHA-256 独立保存。

### T2 原型筛选

1. **扫描后哈希 + 并行键句柄数组：撤回。** `keys-benchmark.jsonl` 的 11 轮筛选中，records 单任务从 10.230 增至 11.242 ms、Unicode 从 11.189 增至 12.411 ms。虽有 16 任务收益，但不以并发改善掩盖单任务回退。
2. **深度 / 属性序号选槽：保留索引思路，撤回单独后扫描比较。** 不对每个键额外遍历哈希；同槽不同内容严格回退，槽不覆盖。单独采用该改动仍未消除回退。
3. **删除并行键数组：保留。** 缓存编号使用 `JsonString` 原有布局空余位；原生节点与字符串描述符均由静态断言保持 12 字节。不为每个属性添加句柄或并行数组。
4. **命中直接替代扫描：保留。** 在扫描键之前，比较已验证键的完整内容和结束引号。只有无转义、非空、非索引、至多 32 个 code unit 的键进入表；任何不匹配或边界不足走原扫描器。1/2/4/8 字节比较使用已有无对齐读辅助函数，其余使用 `memcmp`，不越界读取。
5. **宽对象与普通描述符隔离：保留。** 每个对象只探测前 64 个属性；键计数和命中标记放在现有 8 字节 worker frame 的空余位置，关闭对象时才写回标记，避免逐键读取父 deque 记录。只有前台小子树显式提取缓存编号；普通字符串和通用宽对象不额外解码键缓存元数据。
6. **构建器编译期特化：保留，撤回共用运行时分支。** 在同一个 `BuildJsonObject` 里用运行时条件选择缓存迭代器，曾使同步普通对象解析可重复回退约 6%。最终恢复原两参数入口；缓存入口单独调用同一份内联 `BuildJsonObjectImpl` 的编译期特化。同步路径没有缓存参数和条件分支，也没有复制一份独立对象构建算法。`specialized-sync.jsonl` 的隔离对照中，同步普通对象单 / 四任务为 6.838 → 6.715 ms、25.615 → 25.526 ms。

前台以单次解析内的 64 槽 PersistentHandles 表复用内部化键，和短字符串**值**缓存分离；首次使用仍由原 `MakeString` 按 Map 提示生成键。空字符串仅作未初始化哨兵，因此空键明确排除。对象最终仍交给原 `JSDataObjectBuilder`，字段表示泛化、重复键、字典退化、失效 Map 和 GC 写屏障没有绕过。通用宽 / 深对象与 reviver 构建路径不使用该前台快速表。

### T3 中间表示与内存决策

- 保留已有 12 字节 deque 记录、顺序游标和分片后前缀回收。新 key slot 没有扩大每条记录或 `JsonProperty` 中的字符串描述符。
- worker frame 也由静态断言维持 8 字节，没有因为每层键计数扩大深层结构栈。
- 每个 worker 增加 64 个 `uint32_t` 的键索引表，即 256 字节；每个异步状态增加 64 个 Handle，并仅在前台需要时创建 64 个持久根槽。x64 下两者逻辑槽位共 1024 字节，另有实际分配器 / handle 块粒度。缓存有界，不随输入属性数增长；不是全局 intern 池。
- **不引入按在途字节的全局等待队列。** 仅限制正在扫描的任务不能限制已在入口复制的全部输入；阻塞共享平台 worker 等待 JSON 配额还会占用其他 V8 任务的线程。要实现真正字节预算，需要在调用方延迟复制并约束已完成 tape 的发布 / 生命周期，是独立的 admission-control 契约，而非一个信号量即可完成的优化。本轮用固定并发 RSS 与额外线程容量扫描判断压力，不拿限线程当实现收益。

### T4 流水线与输入复制决策

- **暂不发布同文档的可变 tape。** 当前 worker 完成后发布，容器 `end/count/depth` 在关闭时才完整；前台大数组按最终长度分配。直接边写边读会让 deque 访问、容器回填、缓存引用和前缀回收发生竞争。正确实现需要独立不可变块、发布 / 取消协议，并解决未知长度数组的构建成本。多文档已经能够 worker / 前台交叠，本轮并发目标不要求这项大改。
- **不借用普通 V8 字符串的裸指针。** 当前入口在调用方 ToString、Flatten 后复制，并由 worker 独占原生副本；前台使用持久根保护的原字符串。根能保证对象存活，但不能保证原字符地址不因 GC 或表示变化而改变。外部字符串也不能在没有独立资源所有权契约时直接借用。减少复制需要新的稳定输入所有权接口，不能通过省略拷贝冒险实现。
- 输入复制、单个巨大分配、GC、宽对象最终构建和 reviver 仍可能产生长任务；2 ms 仍是软预算。以上是本轮明确不实施的架构分支，不宣称已经实现流水化或零复制。

| 转义字符串 strings | 1.922 → 1.855 | 7.738 → 7.658 | 7.817 → 7.726 |

| 长字符串 long_strings | 2.264 → 2.255 | 5.581 → 5.466 | 5.606 → 5.633 |
| Unicode | 10.493 → 10.172 | 27.125 → 25.399 | 24.924 → 24.208 |

### 固定 8 worker，16 任务

异步独立模式，每进程 20 轮。CPU 是整个子进程的 user + system 秒数，包含输入准备、显式 GC 和全部轮次，不是单次解析 CPU；RSS 是进程峰值 MiB，不是单份 JSON 占用。

| 场景 / 顺序 | 完成 ms：基线 → 本轮 | 耗时降低 | 进程 CPU s：基线 → 本轮 | 峰值 RSS MiB：基线 → 本轮 |
| --- | ---: | ---: | ---: | ---: |
| 普通对象，正向 | 111.651 → 105.153 | 5.8% | 7.108 → 7.324 | 501.6 → 543.9 |
| 普通对象，反向 | 113.861 → 101.620 | 10.8% | 7.309 → 7.038 | 536.4 → 517.5 |
| 变化值，正向 | 60.261 → 52.108 | 13.5% | 4.123 → 3.923 | 446.1 → 445.7 |
| 变化值，反向 | 58.921 → 51.190 | 13.1% | 4.001 → 3.944 | 410.9 → 441.1 |

完成时间收益在反向复测保留。**普通对象 CPU 没有一致下降，RSS 也不是普遍降低**；有界缓存不等于整体内存配额。相关原始记录为 `verified-concurrency*.jsonl`。不挑选仅有利的运行来承诺 CPU / 内存收益。

### 独立同步控制

`specialized-sync.jsonl` 与反向 `verified-sync-control.jsonl` 均为 20 轮、4 worker、只执行同步解析。普通对象单任务变化分别为 6.838 → 6.715 ms、6.920 → 7.105 ms；四任务分别为 25.615 → 25.526 ms、26.325 → 25.808 ms。先前运行时适配的约 6% 回退不再重复出现；单任务仍有约 ±3% 波动。同步解析控制不混入异步分配 / GC 状态。

只用最终候选、16 个并发任务、每项 11 轮。**不与 20 轮对照的进程 CPU 直接比较，也不作为代码优化的加速比例。**

## 复现与交付

```sh
# BASE / NEW 指向独立构建并保存的基线与本轮 d8。
python3 test/json/parse-async-benchmark.py "$BASE" "$NEW" \
  --runs 20 --workers 4 --cases records numbers strings nested varied \
  long_strings unicode key_churn wide_objects key_collisions
python3 test/json/parse-async-benchmark.py "$BASE" "$NEW" \
  --runs 20 --workers 8 --jobs 16 --mode async --cases records varied
# 交换 BASE / NEW 再执行；同步控制使用 --mode sync。
out/json-opt-release/d8 --expose-gc --thread-pool-size=4 test/json/parse-async.js
out/json-async/d8 --expose-gc --stress-compaction --thread-pool-size=4 \
  test/json/parse-async.js
```
